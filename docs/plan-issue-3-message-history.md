# Issue 3：服务端消息持久化与历史同步方案

## 背景

用户反馈：新加入的设备，或曾经离线的设备重新上线后，看不到其他设备之间已经发送过的聊天记录。用户理解记录保存在服务器缓存目录中，因此期望任意设备上线后都能读取历史。

相关 Issue：<https://github.com/turboxing/ChatTransfer/issues/3>

## 现状分析

当前实现与用户预期的差异：

1. 聊天记录保存在每个浏览器自己的 `localStorage` 中，键为 `im_chat_record`。
2. 服务端只负责消息实时转发，不保存文本消息、文件消息或会话索引。
3. 上传文件保存在服务器缓存目录，但消息记录本身没有落盘。
4. 新设备、换浏览器或清理浏览器数据后，无法读取其他设备的历史。
5. 私聊消息只有在接收方在线时才会被转发；接收方离线期间收到的消息不会补发。
6. 群聊消息只广播给当时在线的成员；新加入设备无法回看历史。

因此，用户看到的现象是当前架构限制，不是缓存目录读取失败。

## 目标

1. 服务端持久化群聊与私聊消息。
2. 新设备上线后可以拉取当前会话历史。
3. 离线设备重新上线后可以同步错过的新消息。
4. 私聊消息在接收方离线时先持久化，接收方上线后再同步。
5. 文件消息与文本消息使用同一套历史同步机制。
6. 保留现有实时聊天体验，不引入账号体系或云服务。

## 已确认产品决策

1. 删除记录拆分为两个动作：
   - **清空我的本地记录**：只影响当前浏览器，不删除服务器历史和物理文件。
   - **清空服务器会话历史**：删除该会话全部消息和关联文件，所有设备都无法恢复。
2. 不采用“每个用户每个会话记录删除游标”的方案，避免形成“仅自己不可见但数据仍保留”的模糊删除语义。
3. 服务器全局清空放在危险操作区，必须二次确认，并明确提示影响所有设备。
4. 在 SQLite 历史上线后，增加私聊入口与会话侧边栏，先支持默认群聊与一对一私聊，不扩展多群聊。

## 非目标

1. 不做多服务器集群同步。
2. 不引入登录、鉴权或账号体系。
3. 不做端到端加密。
4. 不默认上传任何数据到外部服务。
5. 不承诺无限历史；第一版以本机缓存目录可承载的规模为准。

## 用户故事

### 故事 1：新设备查看群聊历史

作为新加入局域网聊天的用户，我希望打开聊天页面后能看到之前的群聊消息，以便理解上下文，而不需要其他用户重新发送。

### 故事 2：离线设备补收私聊消息

作为暂时离线的用户，我希望重新上线后能看到离线期间发给我的私聊消息，以便不遗漏重要内容。

### 故事 3：跨浏览器保留记录

作为更换浏览器或清理浏览器缓存的用户，我希望服务器仍能恢复我的聊天记录，以便继续使用而不丢失上下文。

### 故事 4：文件消息可回看

作为收到文件的用户，我希望历史记录中保留文件名称、大小和下载入口，以便后续重新打开或下载。

### 故事 5：清理历史

作为用户，我希望可以明确清理服务器端历史记录，并知道这会影响所有设备，以便控制本机缓存内容。

## 功能需求

### FR1：服务端消息持久化

1. 服务端接收 `group_chat` 与 `private_chat` 后，先将消息写入本地历史存储。
2. 写入成功后再广播或投递。
3. 每条消息必须有服务端生成的唯一 `msgId`。
4. 消息写入失败时，不向发送方返回成功，也不广播半成品消息。
5. 历史存储位置必须跟随当前缓存目录配置。

### FR2：会话维度存储

1. 群聊会话固定为 `group_chat`。
2. 私聊会话由两个用户 ID 组成，与消息方向无关。
3. 同一对用户的私聊历史应共享一个会话。
4. 会话 ID 不得直接使用用户输入拼接，必须经过安全编码或哈希，避免路径穿越。

### FR3：新设备历史拉取

1. 客户端连接成功后，根据当前 `targetUser` 请求历史。
2. 服务端返回当前会话最近一段历史。
3. 默认返回条数建议为 `100`。
4. 支持分页或游标加载更早消息。
5. 返回消息必须按时间升序排列。

### FR4：增量同步

1. 客户端记录已同步的最后一条消息游标。
2. 断线重连后，只拉取游标之后的新消息。
3. 服务端返回是否存在更多历史。
4. 客户端按 `msgId` 去重，避免重复显示。

### FR5：离线消息补收

1. 接收方离线时，服务端仍持久化私聊消息。
2. 群成员离线时，服务端仍持久化群聊消息。
3. 用户重新上线后，服务端推送未读数量或直接触发增量同步。
4. 私聊历史只允许会话双方拉取。
5. 不向无关用户广播私聊消息。
6. 群聊历史允许已加入群聊的成员拉取。

### FR6：文件消息历史

1. 文件上传成功后，消息记录必须包含文件元数据。
2. 历史记录应保存相对文件路径，而不是依赖当前主机 IP 的绝对 URL。
3. 返回历史时，服务端根据当前请求生成可访问的文件 URL。
4. 文件消息应保留：
   - 文件名
   - 文件大小
   - MIME 类型
   - 相对路径
   - 上传时间

### FR7：旧历史兼容

当前线上使用人数少，且多为临时使用场景，第一版不做旧历史迁移：

1. 不迁移浏览器 `localStorage` 中的旧消息。
2. 功能上线后，只持久化新产生的消息。
3. 旧本地记录仍可留在当前浏览器中，但不作为服务端历史来源。
4. 前端可以继续用本地记录做临时展示缓存，但同步结果以 SQLite 为准。
5. 如后续确有需求，再单独评估旧历史导入工具。

### FR8：清空历史

#### FR8.1：清空我的本地记录

1. 只清理当前浏览器中的本地展示缓存和当前内存消息列表。
2. 不调用服务端删除接口。
3. 不删除服务器 SQLite 历史。
4. 不删除缓存目录中的物理文件。
5. 不影响其他浏览器和其他设备。
6. 清空后重新进入会话，仍可从服务端拉取历史。
7. 第一版建议按当前会话清理本地缓存，避免一次误操作清掉所有会话的本地展示。

#### FR8.2：清空服务器会话历史

1. 删除该会话下的所有消息记录。
2. 删除该会话消息引用的文件，包括文本、图片和普通文件消息对应的物理文件。
3. 删除成功后广播 `history_cleared`。
4. 所有在线客户端收到事件后清空当前会话展示。
5. 操作必须放在危险操作区，并使用二次确认。
6. 确认文案必须明确说明：“将删除该会话的所有消息和文件，所有设备都无法恢复。”
7. 删除消息记录与删除物理文件不能放在同一个数据库事务中，必须设计补偿机制。
8. 清理时先把待删除文件写入清理队列，再提交删除消息的事务。
9. 事务提交后尝试删除物理文件，成功后移除清理队列记录。
10. 删除失败时返回明确错误，保留清理队列记录，并在服务重启或用户重试时继续清理。
11. 如果文件被其他会话消息引用，不能直接删除，需先确认没有其他引用。

### FR9：缓存目录迁移

1. 修改缓存目录时，历史文件必须随现有文件一起迁移。
2. 迁移过程中不能出现部分历史丢失。
3. 迁移失败时不切换配置。
4. 重启后从新缓存目录读取历史。

### FR10：私聊入口与会话侧边栏

1. 增加会话侧边栏，默认包含群聊会话。
2. 侧边栏展示在线用户列表，点击某个用户进入与该用户的一对一会话。
3. 私聊会话不需要显式创建，由当前用户 ID 与对方用户 ID 生成确定性会话。
4. 用户 ID 需要持久化在当前浏览器中，避免每次登录都生成新身份导致私聊历史无法延续。
5. 会话侧边栏应展示会话类型、对方昵称、在线状态和最近消息摘要。
6. 切换会话时只切换当前目标用户，不重建 Socket 连接。
7. 第一版只支持默认群聊与一对一私聊，不引入多群聊、好友关系或账号体系。
8. 后续如需一对多传输，优先评估多群聊，不用“同时发送多个私聊”模拟群聊。

## 数据模型

### 消息记录

建议字段：

```json
{
  "msgId": "server-generated-id",
  "clientMsgId": "optional-client-id",
  "chatType": "group",
  "sender": "user-id",
  "receiver": "group_chat",
  "msgType": "TEXT",
  "content": "message text",
  "senderNickname": "nickname",
  "senderIp": "192.168.0.10",
  "createTime": "YYYY-MM-DD HH:mm:ss",
  "createdAt": 1760000000000,
  "file": {
    "name": "example.png",
    "size": 1024,
    "mimetype": "image/png",
    "relativePath": "files/example.png"
  }
}
```

说明：

1. `msgId` 由服务端生成，推荐 UUID 或稳定递增 ID。
2. `createdAt` 用于排序和游标。
3. `createTime` 保留现有展示格式。
4. `file` 仅文件消息存在。
5. 不保存遥测数据。

### 会话索引

群聊：

```json
{
  "sessionId": "group",
  "chatType": "group",
  "participants": []
}
```

私聊：

```json
{
  "sessionId": "private-<hash>",
  "chatType": "private",
  "participants": ["user-a", "user-b"]
}
```

## 存储方案

### 第一版推荐：SQLite

采用 SQLite 作为唯一服务端历史存储：

```text
<cachePath>/
└── history/
    └── chattransfer.db
```

#### 依赖选择

推荐使用 `sqlite3@5.1.7`：

1. 提供 N-API 预编译二进制。
2. 与当前 `pkg@5.8.1` 的 `node18-macos-x64` 和 `node18-win-x64` 目标兼容。
3. 已在 macOS 上完成最小可执行文件验证。
4. 已在 macOS 上交叉生成 Windows PE 可执行文件，但尚未完成 Windows 真机运行验证。
5. API 为异步模式，适合避免阻塞 Socket.IO 事件循环。

不推荐当前使用 `better-sqlite3@11.10.0`：

1. 在当前 Node 24 环境安装后，原生模块按 `NODE_MODULE_VERSION 137` 编译。
2. 当前 `pkg` 运行时为 Node 18，要求 `NODE_MODULE_VERSION 108`。
3. 直接打包会报 `ERR_DLOPEN_FAILED`。
4. 未找到可用的 Node 18 预编译包。

#### 打包结论

`pkg` 会把原生 `.node` 文件打进可执行文件，并在运行时释放到临时目录后加载。数据库文件本身仍保存在缓存目录，不写入可执行文件。

#### 跨平台兼容性评估

SQLite 数据库文件本身与操作系统无关，只要使用同一套 SQLite 访问层，缓存目录中的 `chattransfer.db` 可以在 macOS、Windows 和 Linux 之间复制使用。

需要区分的是 `sqlite3` 原生模块：

1. `sqlite3@5.1.7` 使用 N-API 3/6，同一操作系统和架构下的二进制可以兼容 Node 18、20、24 等支持对应 N-API 的运行时。
2. `.node` 文件是平台和架构相关的，macOS x64、Windows x64、Linux x64 需要各自的原生二进制。
3. 在一个操作系统上用 `pkg` 交叉打包另一个目标时，不能默认认为当前安装的 `.node` 文件可用于目标系统。
4. 当前发布目标只有 macOS x64 与 Windows x64；如果未来增加 Linux 或 macOS arm64，需要先补充对应目标的打包和运行验证。

#### 发布策略

为保证原生模块确实被打进可执行文件，发布流程应按目标系统原生构建：

1. macOS x64 包在 macOS x64 runner 上执行 `npm ci` 与 `pkg -t node18-macos-x64`。
2. Windows x64 包在 Windows x64 runner 上执行 `npm ci` 与 `pkg -t node18-win-x64`。
3. 每个目标产物必须在对应系统上完成启动、建库、写入、读取的冒烟测试。
4. 不建议继续只在一个 Linux runner 上交叉打包 macOS 和 Windows，因为原生模块容易带入错误平台的二进制。
5. 如果确需保留交叉打包，必须显式准备每个目标平台的 `.node` 文件，并在打包后做字节码与运行时校验；该方案复杂度更高，第一版不推荐。

已验证：

1. `sqlite3@5.1.7`
2. `pkg@5.8.1`
3. `node18-macos-x64`
4. `node18-win-x64`

验证结果：

```text
node 运行：{"runtime":"node","value":"ok"}
pkg 运行：{"runtime":"pkg","value":"ok"}
Windows 交叉打包：PE32+ executable (console) x86-64
```

验证边界：

1. macOS x64 的 Node 与 `pkg` 可执行文件已完成实际运行验证。
2. Windows x64 目前只验证了交叉打包产物格式，还没有在 Windows 真机上验证 SQLite 读写。
3. 正式实现后必须把 Windows 真机或对应平台 CI runner 的运行验证加入发布门禁。

## 服务端设计

新增模块：

```text
server/services/message-history-service.js
```

职责：

1. 创建历史目录与 SQLite 数据库。
2. 生成会话 ID。
3. 写入消息。
4. 查询历史。
5. 删除会话历史与关联文件。
6. 处理数据库错误。
7. 限制查询条数。
8. 管理数据库连接生命周期。

存储逻辑不应直接写在 Socket 处理器中。

## Socket 协议

### 请求历史

客户端发送：

```json
{
  "chatType": "group",
  "targetUser": "group_chat",
  "cursor": null,
  "limit": 100
}
```

服务端 ack 返回：

```json
{
  "code": 0,
  "data": {
    "messages": [],
    "hasMore": false,
    "nextCursor": "last-msg-id"
  }
}
```

### 清空服务器会话历史

客户端发送：

```json
{
  "chatType": "group",
  "targetUser": "group_chat"
}
```

服务端广播：

```json
{
  "chatType": "group",
  "sessionId": "group"
}
```

## 前端设计

1. `useSocket` 增加历史同步事件。
2. `useMessages` 改为以服务端历史为主。
3. 连接成功后：
   - 拉取服务端历史
   - 进入实时消息模式
4. 收到实时消息时，同时更新内存列表与本地缓存。
5. 断线重连后使用游标增量同步。
6. 服务器全局清空时调用服务端删除接口。
7. 不迁移旧 `localStorage` 历史。
8. “清空我的本地记录”只处理本地缓存和内存列表。
9. “清空服务器会话历史”调用服务端删除接口，并处理 `history_cleared` 事件。
10. 增加会话侧边栏组件，支持群聊与私聊切换。
11. 在线用户列表作为私聊入口，点击用户后切换 `targetUser`。
12. 用户 ID 与昵称分别持久化，用户 ID 不随每次登录重新生成。

## 安全与隐私

1. 历史数据只保存在本机缓存目录。
2. 不向外部服务上传消息内容。
3. 遥测不得采集消息内容、文件名或会话参与者。
4. 私聊历史必须校验请求者是否为会话参与者。
5. 会话文件名必须使用哈希或安全编码，避免路径穿越。
6. 文件路径必须限制在缓存目录内。
7. 消息字段需要限制长度，避免异常大 payload。

## 异常处理

1. 历史目录不存在时自动创建。
2. SQLite 文件损坏时返回明确错误，并停止历史服务。
3. 写入失败时返回错误，不广播消息。
4. 读取失败时前端显示历史同步失败。
5. 迁移失败时保留原缓存目录配置。
6. 清理失败时返回明确错误。

### Socket E2E 测试

1. A 发送群聊消息，B 和 C 在线实时收到。
2. D 后上线，能拉取历史群消息。
3. A 向离线 B 发送私聊消息。
4. B 上线后能同步该私聊消息。
5. B 离线期间，群聊仍有新消息。
6. B 上线后能同步错过的群聊消息。
7. C 无法读取 A 与 B 的私聊历史。

## 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 历史文件增长过快 | 磁盘占用增加 | 提供保留策略与清理入口 |
| SQLite 文件损坏 | 历史不可读 | 返回明确错误并保留原文件 |
| 原生模块与 pkg 运行时不匹配 | 可执行文件启动失败 | 使用已验证的 sqlite3@5.1.7 与 Node 18 目标 |
| 删除文件失败 | 磁盘空间未释放 | 记录失败路径并提供重试 |
| 交叉打包带入错误平台原生模块 | 对应系统可执行文件启动失败 | 按目标系统原生构建并增加运行冒烟测试 |
| 私聊权限不足 | 历史可能被无关用户读取 | 校验会话参与者 |
| 缓存目录迁移失败 | 历史丢失 | 失败时不切换配置 |
