# 多房间会话需求方案

## 1. 结论

建议将 ChatTransfer 的“群聊”概念统一升级为“房间”。房间是消息、文件、成员和在线状态的基本隔离单位。后续不再单独设计私聊模型；一对一传输可以理解为一个只有两台设备的房间。

用户可以通过扫码或房间码加入房间，也可以创建新房间用于不同项目、不同设备组合或不同协作场景。这样可以避免所有内容都进入“公共大厅”，同时保留新设备扫码加入的低成本路径。

## 2. 现状

当前产品只有一个供所有设备共用的“公共大厅”：

- 客户端通过 `group_online` 进入同一个 Socket.IO 房间 `group-chat`。
- 消息、文件、历史记录、附件和批量下载都围绕当前默认会话组织。
- 服务端使用 `RoomManager` 维护用户在线状态，最近版本已支持同一用户多个 Socket 连接和离线防抖。
- SQLite 已有 `sessions`、`session_participants`、`messages` 等表，可以按会话保存消息。
- 前端顶部已经预留左侧位置，可用于后续会话切换入口。
- 用户可以通过扫码进入当前公共大厅，但没有多房间、房间码或手动加入房间能力。

## 3. 痛点

1. **所有内容集中在公共大厅**
   不同项目、不同设备组合、不同协作对象的内容混在一起，后续查找历史消息和文件较困难。

2. **无法创建独立传输空间**  
   用户有时只想和一台设备传输日志、截图、安装包或临时账号，但不希望这些内容进入公共群聊。

3. **缺少多会话切换能力**  
   当前页面只能展示公共大厅，用户无法快速在多个传输场景之间切换。

4. **设备加入方式单一**  
   目前主要依赖扫码。某些设备不方便扫码时，缺少通过房间码手动加入的入口。

5. **“群聊”概念不够准确**  
   ChatTransfer 的核心场景不是传统即时通讯，而是跨设备临时传输。“群聊”会让用户误以为必须有多个人参与；而“房间”更贴近扫码进入、临时协作、用完即走的产品心智。

## 4. 目标

1. 将“群聊”概念统一为“房间”。
2. 支持创建多个房间，每个房间拥有独立消息、文件和成员状态。
3. 支持扫码加入房间。
4. 支持通过房间码手动加入房间。
5. 支持房间内在线设备列表和上下线提示。
6. 支持无刷新切换房间。
7. 支持成员退出房间、房主解散房间和房主自动移交。
8. 将原“默认房间”统一命名为“公共大厅”，并限制其管理能力。
9. 保持现有公共大厅链接和扫码流程兼容。
10. 为房间历史清理、房间过期和房间销毁提供清晰边界。

## 5. 收益

| 收益 | 说明 |
|---|---|
| 概念统一 | 不再区分群聊与私聊，所有会话都可以表示为房间 |
| 降低加入成本 | 新设备可以扫码或输入房间码快速加入 |
| 内容隔离 | 不同项目、不同设备组合的消息和文件互不干扰 |
| 提升隐私感 | 临时内容可以放在独立房间，避免进入公共大厅 |
| 更好支持多人协作 | 多台测试设备、多个测试项目可以使用不同房间 |
| 复用现有能力 | 历史记录、附件、批量下载、在线设备列表都可以按房间扩展 |

## 6. 用户流程

### 6.1 创建房间

1. 用户点击“新建房间”。
2. 输入房间名称，例如“iOS 测试机传输”“项目 A 临时调试”。
3. 系统生成 `roomId` 和房间码。
4. 用户进入新房间。
5. 系统展示邀请二维码和房间码。
6. 用户可以复制房间码、复制邀请链接，或展示二维码给其他设备扫码。

### 6.2 扫码加入房间

1. 新设备扫描房间邀请二维码。
2. 浏览器打开加入链接。
3. 如果设备没有昵称，提示填写昵称或使用默认昵称。
4. 客户端校验 `roomId` 和房间码。
5. 加入成功后进入房间。
6. 房间保存到本机最近会话列表。

### 6.3 手动加入房间

1. 用户点击“加入房间”。
2. 输入房间码。
3. 服务端根据房间码查找房间。
4. 校验通过后加入房间。
5. 前端加载房间元信息和历史消息。

### 6.4 切换房间

1. 点击顶部左侧会话切换入口。
2. 打开会话侧栏或抽屉。
3. 展示最近房间、当前房间、在线人数和最后消息时间。
4. 选择目标房间。
5. 前端无刷新切换 Socket 房间和历史消息。
6. 清理当前页面的附件选择、Pin 状态、临时提示和输入状态。

### 6.5 房间生命周期、退出与解散

必须区分“退出房间”“解散房间”“清空服务器记录”和“清空本地记录”，不能用一个“删除会话”同时表达。

#### 6.5.1 退出房间

适用于普通房间内的任意成员：

1. 用户从房间菜单选择“退出房间”。
2. 服务端删除该用户在 `room_participants` 中的成员关系。
3. 服务端将当前 Socket 移出对应 Socket.IO 房间并更新在线列表。
4. 当前设备清理该房间的消息缓存、Pin、置顶、草稿、附件选择和批量下载状态。
5. 其他成员仍可查看历史和继续聊天，不受影响。
6. 用户以后仍可通过有效房间码或邀请链接重新加入。

如果退出者是房主：

- 还有其他成员时，房主身份自动移交给最早加入的剩余成员。
- 没有其他成员时，退出等同于解散房间。

#### 6.5.2 解散房间

仅房主可以解散普通房间：

- 删除或标记删除房间。
- 删除全部房间成员。
- 删除该房间下的全部消息。
- 将关联附件加入现有文件清理队列，仅删除不再被其他消息引用的物理文件。
- 使房间码和未使用的批量下载令牌立即失效。
- 向房间内在线设备广播 `room_deleted`。
- 在线设备清理对应本地状态，并自动切换到公共大厅。

解散属于全局危险操作，必须二次确认，并明确提示：

> 解散房间将删除全部消息、附件和邀请码，所有设备都无法恢复。

#### 6.5.3 清空服务器记录与清空本地记录

- **清空我的本地记录**：任意成员都可以执行，只清理当前设备缓存，不删除服务端消息和文件。
- **清空服务器记录**：普通房间仅房主可以执行，保留房间、成员和房间码，只删除消息及无引用附件。
- 公共大厅不允许普通用户清空服务器记录。

#### 6.5.4 公共大厅

原“默认房间”在产品和文档中统一更名为“公共大厅”，技术 ID 继续保留为 `group_chat`，以兼容旧链接和旧历史。

公共大厅定位为所有设备共用的临时中转区域，不属于任何浏览器用户，因此：

- 在房间列表、聊天标题、常用功能和邀请弹窗中显示建筑图标及“公共”标签，与普通房间明确区分。
- 不设置房主。
- 不允许编辑房间名称。
- 不允许重新生成房间码。
- 不允许退出或解散。
- 不展示房间管理菜单。
- 所有用户只能清空自己的本地记录。
- 服务端消息和附件只能由实例管理员清理。
- 通过 `CHATTRANSFER_PUBLIC_ROOM_RETENTION_DAYS` 配置保留期限，默认 7 天，设置为 `0` 可关闭自动清理。
- 服务启动时及运行期间定期清理超过保留期限的公共大厅消息和无引用附件。

普通房间同时支持闲置自动删除：

- 启动参数：`--room-idle-retention-days <days>`
- 环境变量：`CHATTRANSFER_ROOM_IDLE_RETENTION_DAYS`
- 默认 7 天，设置为 `0` 可关闭
- 仅删除无人在线且超过保留期限的普通房间
- 优先级：启动参数 > 环境变量 > 默认值

实例管理员指运行 ChatTransfer 的宿主机所有者。管理员清理能力应通过以下方式之一授权：

- 仅允许来自 `127.0.0.1` 或 `localhost` 的管理入口。
- 使用配置中的管理员 token。
- 通过服务端 CLI 执行维护命令。

管理员权限必须在服务端校验，不能只依赖前端隐藏按钮。

#### 6.5.5 普通房间闲置自动删除

普通房间由服务端定期检查，不依赖用户在前端主动点击删除：

- 创建、加入、发消息、修改名称或重新生成房间码都会更新 `last_active_at`。
- 仅在房间超过保留期限且当前没有在线设备时删除。
- 服务启动时先完成一次清理，再开始接受连接；运行期间每 6 小时检查一次。
- 软件停止运行期间不会执行删除，恢复运行后按 `last_active_at` 判断是否已过期。
- 删除原因为 `inactive`，复用“解散房间”的消息、成员、附件和清理队列流程。
- 启动参数为 `--room-idle-retention-days`，环境变量为 `CHATTRANSFER_ROOM_IDLE_RETENTION_DAYS`，默认 7 天，`0` 表示关闭。

## 7. 房间模型

### 7.1 房间字段

建议服务端维护以下核心字段：

| 字段 | 说明 |
|---|---|
| `roomId` | 房间唯一标识，建议使用 UUID |
| `name` | 房间名称 |
| `code` | 房间码，用于手动加入 |
| `createdAt` | 创建时间 |
| `updatedAt` | 最后更新时间 |
| `lastMessageAt` | 最近消息时间 |
| `createdBy` | 初始创建者用户 ID，用于审计 |
| `ownerId` | 当前房主用户 ID，创建时等于 `createdBy`，可自动移交 |
| `status` | `active`、`deleted` |
| `deletedAt` | 删除时间，未删除时为空 |
| `deletedReason` | `manual`、`last_member_left` 或 `inactive` |
| `lastActiveAt` | 最后一次有效房间活动时间，用于闲置清理 |

### 7.2 房间码规则

- 使用 8 位随机大写字母和数字。
- 移除容易混淆的字符，例如 `0/O`、`1/I/L`。
- 展示格式建议使用 `XXXX-XXXX`，提高可读性。
- 房间码必须与 `roomId` 一起校验，避免仅靠短码被穷举。
- 支持重新生成房间码；旧房间码立即失效。

### 7.3 公共大厅兼容

为避免旧扫码链接失效，原默认房间映射为：

```text
公共大厅 roomId = group_chat
```

旧参数 `receiver=group_chat`、旧 Socket 房间名和旧历史记录继续兼容。公共大厅不要求房间码；新建房间必须使用房间码。

公共大厅名称由前端本地化展示，服务端不允许通过 `room_update_name` 修改其名称。即使客户端绕过前端直接发送请求，服务端也必须拒绝。

如果后续希望公共大厅也受房间码保护，可以单独设计迁移提示，但不应强制变更所有旧链接。

## 8. 技术方案

### 8.1 服务端数据模型

建议新增以下表或集合：

#### `rooms`

```sql
CREATE TABLE IF NOT EXISTS rooms (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  code TEXT UNIQUE,
  created_by TEXT,
  owner_id TEXT,
  status TEXT NOT NULL DEFAULT 'active',
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL,
  deleted_at INTEGER,
  last_active_at INTEGER,
  deleted_reason TEXT
);
```

#### `room_participants`

用于记录曾经加入过房间的设备或用户：

```sql
CREATE TABLE IF NOT EXISTS room_participants (
  room_id TEXT NOT NULL,
  user_id TEXT NOT NULL,
  role TEXT NOT NULL DEFAULT 'member',
  nickname TEXT,
  joined_at INTEGER NOT NULL,
  last_seen_at INTEGER,
  PRIMARY KEY (room_id, user_id)
);
```

`rooms.owner_id` 保存当前房主；`room_participants.role` 使用 `owner` 或 `member`。房主退出时，应在同一事务中更新这两个字段。`rooms.last_active_at` 应在创建、加入、发消息、改房间名和重新生成房间码时更新。

公共大厅使用 `id = group_chat`、`owner_id = NULL`、`code = NULL`。现有 `sessions` 和 `session_participants` 可以继续用于消息历史隔离；`rooms` 和 `room_participants` 用于房间元数据和房间列表。

### 8.2 Socket 事件

建议新增或调整以下事件：

| 事件 | 说明 |
|---|---|
| `room_create` | 创建房间，返回 `roomId`、房间码和房间名称 |
| `room_join` | 通过 `roomId` 和房间码加入房间 |
| `room_leave` | 当前设备离开房间 |
| `room_dissolve` | 房主解散房间 |
| `room_deleted` | 通知房间内其他设备房间已被解散 |
| `room_owner_changed` | 通知房主发生自动移交 |
| `room_switch` | 客户端切换当前活跃房间 |
| `room_updated` | 房间名称、房间码或状态变化 |
| `room_presence_changed` | 房间内设备上线或离线 |
| `room_history_cleared` | 当前房间服务器历史被清空 |

现有 `group_online`、`group_chat`、`user_list_updated` 等事件可以保留，用于兼容旧客户端；新前端逐步迁移到房间维度事件。

### 8.3 Socket 房间隔离

Socket.IO 中需要从单一 `chatRoom = 'group-chat'` 迁移为按 `roomId` 管理：

```text
room:<roomId>
```

例如：

```text
room:group_chat
room:9f1c2c86-1f80-4d14-9c35-4f7d17d63b18
```

一个 Socket 同时只应位于当前活跃房间。切换房间时：

1. 离开旧 Socket 房间。
2. 加入新 Socket 房间。
3. 重新广播旧房间和新房间的用户列表。
4. 前端加载新房间历史。

### 8.4 房间码校验

手动加入必须校验：

- `roomId` 是否存在。
- 房间状态是否为 `active`。
- 房间码是否匹配。
- 加入频率是否超过限制。

建议在服务端加入简单内存限流或 SQLite 限流记录，避免短时间内被暴力尝试。

### 8.5 历史与文件隔离

所有消息查询、附件查询、批量下载、历史清理都必须带上房间维度：

```text
requester
roomId
```

替代或兼容当前的：

```text
requester
chatType
targetUser
```

为了避免一次性破坏现有客户端，服务端可以暂时兼容旧参数：

- `chatType=group` 且 `targetUser=group_chat` 映射到公共大厅。
- 新前端统一使用 `roomId`。

### 8.6 在线状态

当前在线设备能力按全局用户维护。多房间方案下需要按房间维护：

```text
roomId -> userId -> socketIds
```

同一个人可以同时在线于多个房间，但每个房间只展示当前进入该房间的人。

上下线提示也应限定在当前房间内广播，避免把其他房间的设备状态通知到无关房间。

### 8.7 生命周期与权限校验

服务端应提供统一的房间权限校验方法：

```text
assertRoomMember(roomId, userId)
assertRoomOwner(roomId, userId)
assertAdminRequest(requestContext)
```

所有房间管理操作必须满足：

- `roomId` 必须是有效的活动房间。
- 操作者必须是该房间成员；解散和服务器历史清理还必须是房主。
- 当前 Socket 的 `activeRoomId` 必须与目标 `roomId` 一致。
- 公共大厅拒绝重命名、重新生成房间码、退出和解散。
- 公共大厅服务器清理只允许实例管理员执行。

服务端应新增：

- `leaveRoom({ roomId, userId })`
- `dissolveRoom({ roomId, requester })`
- `transferRoomOwner({ roomId, fromUserId, toUserId })`
- `clearPublicRoomHistory({ requester, adminProof })`

`dissolveRoom` 应在 SQLite 事务中完成房间状态、成员、消息和文件清理队列的更新，避免出现房间已不可访问但附件仍残留，或消息已删除但成员列表仍可见的中间状态。

## 9. 前端方案

### 9.1 顶部布局

保留当前三栏布局：

| 位置 | 内容 |
|---|---|
| 左侧 | 会话切换入口，后续可扩展房间列表 |
| 中间 | 房间名称、连接状态、在线人数 |
| 右侧 | Pin、二维码、常用功能等操作 |

### 9.2 会话侧栏

第一版可以先使用抽屉，避免移动端布局复杂化：

- 公共大厅固定展示且不可删除。
- 最近房间按 `lastMessageAt` 排序。
- 每个房间显示房间名称、在线人数、最后消息时间。
- 当前房间高亮。
- 提供“新建房间”和“通过房间码加入”。
- 普通房间提供 `...` 管理菜单。
- 公共大厅不展示重命名、退出、解散和重新生成房间码入口。

### 9.3 房间邀请

邀请弹窗展示：

- 房间名称。
- 邀请二维码。
- 房间码。
- 复制房间码。
- 复制邀请链接。
- 重新生成房间码。

### 9.4 房间管理入口

普通房间的 `...` 菜单包含：

| 菜单项 | 权限 | 说明 |
|---|---|---|
| 邀请加入 | 房间成员 | 展示二维码、房间码和邀请链接 |
| 编辑名称 | 房主 | 公共大厅不显示 |
| 退出房间 | 房间成员 | 只影响当前设备和成员关系 |
| 解散房间 | 房主 | 全局删除，使用危险操作二次确认 |

退出或解散后，如果当前房间不可继续使用，前端应切换到公共大厅，并清理旧房间的本地状态。

### 9.5 状态清理

切换房间时必须清理：

- 当前输入内容。
- 未上传完成的文件卡片。
- 附件多选状态。
- Pin 和置顶状态。
- 滚动位置。
- 上下线临时提示。
- 批量下载弹窗状态。

## 10. 权限与安全

当前产品没有账号体系，普通房间以房间码为主要访问边界，公共大厅默认对所有能访问服务的设备开放。

第一版应遵循以下原则：

- 知道 `roomId` 和房间码的人可以加入房间。
- 不知道房间码的人不能通过手动加入进入。
- 房间码可以随时重新生成。
- 房间内历史和附件只能由房间内用户访问。
- 任意成员可以退出普通房间，但不能清空服务器记录或解散房间。
- 房主可以编辑房间名称、重新生成房间码、清空服务器记录和解散房间。
- 房主退出时自动移交给最早加入的剩余成员；没有剩余成员时自动解散。
- 最后一个成员退出普通房间时，服务端自动解散并清理房间。
- 公共大厅没有房主，普通用户只能清空本地记录；服务器记录只能由实例管理员清理。
- 公共大厅不允许编辑名称、重新生成房间码、退出或解散。
- 不实现端到端加密；服务端仍然可以看到消息内容。
- 局域网内仍建议配合防火墙、内网隔离和临时房间使用。

由于浏览器端 `userId` 存在 localStorage 中，房主权限第一版只能防止误操作，不能提供账号级安全保证。若后续面向不可信网络或多人环境，应增加服务端签发的 `ownerToken`，并在解散、重命名和重新生成房间码时校验。

## 14. 验收标准

1. 用户可以创建新房间并获得房间码和邀请二维码。
2. 新设备可以通过扫码加入房间。
3. 新设备可以通过输入房间码加入房间。
4. 不同房间之间的消息、文件和在线设备互不可见。
5. 切换房间时不刷新页面，历史消息正确加载。
6. 旧 `group_chat` 链接和旧历史记录仍然可用。
7. 房间内批量下载只能选择当前房间的附件。
8. 清空房间历史只影响当前房间。
9. 重新生成房间码后，旧房间码不能加入。
10. 任意普通房间成员可以选择退出房间，退出后该房间不再出现在自己的会话列表中。
11. 退出房间不会影响其他成员的聊天记录和文件。
12. 房主退出且仍有其他成员时，房主身份自动移交给最早加入的剩余成员。
13. 房主解散房间后，所有在线设备收到通知并切换到公共大厅。
14. 最后一个成员退出后，房间、消息和无引用附件被自动清理。
15. 公共大厅始终显示为“公共大厅”，任何普通用户都不能修改名称。
16. 公共大厅在房间列表和聊天标题中显示“公共”特殊标识。
17. 公共大厅不提供退出、解散和重新生成房间码入口。
18. 普通用户不能在公共大厅清空服务器消息和附件，只能清空本地记录。
19. 实例管理员可以在受信任入口清理公共大厅服务器记录。
20. 移动端和桌面端布局均可用，且无状态残留。
21. 普通房间超过闲置期限且无人在线时，会在启动清理或下一次定时清理中删除。
22. 启动软件本身不重置闲置计时，只有实际房间活动才重置。

## 15. 风险与约束

| 风险 | 说明 | 缓解方式 |
|---|---|---|
| 房间码泄露 | 知道房间码的人可以加入 | 支持重新生成房间码，后续可增加过期时间 |
| 无账号体系 | 清理浏览器数据后可能丢失本机会话列表 | 用户可重新扫码或输入房间码加入 |
| 旧链接兼容 | 旧二维码和链接不能失效 | 保留 `group_chat` 公共大厅映射 |
| Socket 状态迁移复杂 | 全局事件和用户列表需要按房间拆分 | 分阶段迁移，先兼容旧事件 |
| 本地状态残留 | 切换房间后可能出现消息、Pin 或附件错乱 | 建立统一切换清理流程 |
| 服务端数据增长 | 多房间会增加历史和文件占用 | 后续增加房间过期和自动清理 |
| 误解散 | 房主可能误删整个房间 | 仅房主可见、二次确认、明确全设备不可恢复 |
| 房主身份丢失 | 浏览器数据清理后无法证明房主身份 | 第一版按局域网可信设备处理；后续增加 `ownerToken` |
| 公共大厅被清空 | 公共大厅没有房主，普通用户可能误操作 | 普通用户只允许清空本地记录；服务器清理仅实例管理员可执行 |
| 孤儿房间 | 用户直接关闭设备而不执行退出 | 最后成员退出自动解散；后续增加未活跃房间过期清理 |
