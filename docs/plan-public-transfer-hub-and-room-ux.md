# 公共中转站启动体验与房间管理优化需求

- 状态：已实现
- 日期：2026-11-09
- 范围：启动页与公共中转站、设备连接状态、房主级自动清理、会话排序稳定性
- 关联文档：[多房间会话需求方案](./plan-multi-room-conversations.md)、[ChatTransfer Backlog](./backlog.md)

## 1. 背景

ChatTransfer 当前启动后会先打开独立首页。首页展示公共房间二维码，扫码设备会进入 `group_chat`，电脑端需要手动点击 `STEP2` 后才能进入同一个房间。

当前流程有三个明显问题：

1. 扫码设备已经进入房间，但电脑端仍停留在首页，电脑无法看到哪些设备已经加入。
2. `STEP1 / STEP2` 看起来像“所有设备准备好后再开始”的门槛，但实际只控制电脑端进入房间，概念与行为不一致。
3. 首页和公共房间维护同一会话的两个状态阶段，用户需要多一次跳转，后续增加多设备准备区也会造成状态分裂。

同时，现有房间管理还有两项使用体验问题：

1. 普通房间的闲置清理周期由服务端全局配置控制，房主无法针对单个房间选择 7 天、30 天或永不自动清理。
2. 会话列表当前按参与者的 `last_seen_at` 排序；用户点击或切换会话时会更新最后访问时间，导致仅仅点击会话也会改变列表顺序，而不是只有新消息才置顶。

本方案将独立首页改为“公共中转站”，把设备连接状态直接放进公共中转站，并补充房主级自动清理和稳定会话排序规则。

## 2. 目标

1. 将“公共大厅”统一改名为“公共中转站”，技术房间 ID 继续使用 `group_chat`。
2. 软件启动后直接进入公共中转站，不再要求点击 `STEP2`。
3. 电脑端实时展示扫码设备的连接数量、设备信息和上下线状态。
4. 公共中转站没有其他设备时，用清晰的接入引导展示二维码；有设备后自动弱化引导，不阻塞聊天。
5. 普通房间的当前房主可以在会话菜单中选择自动清理周期。
6. 会话列表只在收到或成功发送新消息时置顶，点击、切换、刷新或在线状态变化不得改变顺序。
7. 保持旧二维码、旧链接、历史记录和多房间能力兼容。

## 3. 非目标

本版本不包含以下能力：

- 账号体系、登录鉴权或跨服务器身份同步。
- 端到端加密。
- 跨服务器实时消息通知。
- 未激活房间的全局未读角标或推送通知。
- 任意天数的手动输入；第一版提供固定清理策略。
- 设备详细指纹采集、型号识别或定位。
- 公共中转站房主、解散、退出或改名能力。
- 改变公共中转站消息保留策略；该策略仍由实例管理员配置。

## 4. 术语与定义

| 术语 | 定义 |
|---|---|
| 公共中转站 | 所有可访问同一服务的设备共用的默认房间，技术 ID 为 `group_chat`，无房主，不可改名、退出或解散 |
| 普通房间 | 用户创建、可扫码或输入房间码加入的独立房间，有房主和房间码 |
| 本机 | 当前打开页面的设备或浏览器实例 |
| 其他设备 | 除本机外，当前已加入同一房间的在线设备 |
| 自动清理 | 普通房间长期无人使用时，服务端删除房间、消息和无引用附件的行为 |
| 会话置顶排序 | 会话列表按最近消息时间排序，而不是按用户点击或最后访问时间排序 |
| 本地记录 | 当前浏览器 localStorage 中保存的消息、草稿和其他本地状态 |

## 5. 产品原则

1. **房间即状态**：启动页就是公共中转站，不再用独立页面模拟“准备中”状态。
2. **不制造伪门槛**：设备是否全部准备好由用户自行判断，系统展示真实在线状态，但不用按钮阻塞开始传输。
3. **真实连接才算设备在线**：设备数量必须来自 Socket.IO 房间成员，不使用二维码访问次数或页面 PV。
4. **非阻塞引导**：二维码和连接提示不能遮挡已有聊天记录，也不能阻止用户立即发送内容。
5. **排序可预期**：只有新消息才能改变会话顺序，点击会话只改变选中状态。
6. **危险操作可理解**：自动清理和永不清理都要明确说明手动解散、成员退出和服务器清理仍然会生效。

## 7. 详细需求

### 7.1 HUB-01：统一更名为“公共中转站”

#### 展示名称

- 中文：`公共中转站`
- 英文：`Public Transfer Hub`
- 阿拉伯语：使用与“公共传输空间/公共中转空间”一致的正式翻译，并在发布前完成本地化审校。

#### 规则

1. 所有用户可见文案中的“公共大厅”统一替换为“公共中转站”。
2. 技术 ID 继续使用 `group_chat`，不得修改，以兼容旧链接和历史记录。
3. 房间列表和聊天标题继续显示“公共”特殊标识，用于和普通房间区分。
4. 公共中转站不显示房主菜单，不允许改名、重新生成房间码、退出、解散或自定义自动清理。
5. 公共中转站消息保留期限继续由实例管理员通过 `CHATTRANSFER_PUBLIC_ROOM_RETENTION_DAYS` 控制。
6. 三语 README、UI 文案、帮助说明、更新记录和文档中的名称保持一致。

#### 验收

- 中文界面所有用户可见位置均显示“公共中转站”。
- 英文和阿拉伯语界面不残留旧名称。
- 旧 `receiver=group_chat` 链接仍可进入公共中转站。
- 公共中转站没有房主管理入口。

### 7.2 HUB-02：启动后直接进入公共中转站

#### 流程

1. 软件启动并打开浏览器。
2. 浏览器直接进入公共中转站，不再展示独立欢迎首页。
3. 本机自动生成或恢复身份并加入 `group_chat`。
4. 页面加载公共中转站历史记录和设备状态。
5. 桌面端启动后，在屏幕中央、视图最上层展示设备连接弹窗；手机端不自动展示，通过右上角 `添加设备` 按需打开。
6. 扫码设备进入后自动加入公共中转站，电脑端无需额外点击进入。

#### 兼容要求

- 根路径 `/` 必须直接进入公共中转站，不得要求用户点击 `STEP2`。
- 现有 `/chat?receiver=group_chat` 链接继续可用。
- 现有扫码中转页可以保留，但扫码完成后应直接进入目标房间，不返回独立首页。
- 现有 `getIndexInfo2?receiver=group_chat` 二维码接口保持兼容。
- 访问旧首页链接时必须自动进入公共中转站。

#### 文案要求

- 删除 `STEP1`、`STEP2`、`点我开始使用` 等阶段式文案。
- 使用 `添加设备`、`扫码加入公共中转站`、`已连接`、`现在可以开始传输` 等直接描述状态的文案。
- 欢迎语不能长期占据聊天主体区域。

### 7.3 HUB-03：邀请加入房间弹窗

#### 展示条件

- 桌面端启动并进入公共中转站时，自动在屏幕中央展示。
- 手机端启动时不自动展示，也不在聊天顶部占用空间。
- 用户主动收起后不再展示；点击右上角 `添加设备` 可重新打开同一弹窗。
- 当前房间不是公共中转站时，不展示该弹窗。

#### 内容

1. 弹窗头部左侧展示标题：`邀请加入房间`
2. 顶部中央展示房间名称，`公共` 标签位于公共中转站名称左侧；公共中转站没有房间码，因此使用房间名称作为标识
3. 二维码：
   - 加载中显示骨架或 Loading。
   - 获取失败显示明确错误和重试按钮。
   - 桌面端二维码展示尺寸为 320px，移动端为 260px 左右，并使用高分辨率图片。
   - 点击二维码可以打开全屏预览，便于远距离扫码。
   - 桌面端和移动端均使用上下布局，二维码居中展示。
4. 本机状态：`本机已连接`；状态、设备列表、邀请操作和步骤说明均位于二维码下方
5. 辅助操作：
   - `复制邀请链接`
   - `收起连接区`
   - 如后续支持手动加入，可增加 `设备不方便扫码？`
6. 轻量步骤提示，不使用 STEP 编号：
   - `扫码`
   - `设备自动加入`
   - `开始传输`

#### 设备加入后的保留规则

- 第一台其他设备加入后，二维码不得自动消失。
- 收到或发送消息不得自动收起弹窗。
- 在线设备状态文案可点击：桌面端打开设备连接侧边栏，手机端在弹窗内展开设备列表；再次点击同一状态可关闭。
- 手机端展开设备列表时暂时隐藏二维码区域，保证列表完整可见；关闭列表后二维码恢复。
- 设备连接侧边栏挂在页面顶层，避免被连接弹窗遮挡。
- 只有用户主动点击 `收起连接区` 时才折叠。
- 收起后弹窗关闭，通过右上角 `添加设备` 打开同一弹窗。
- 桌面端页面刷新后弹窗默认重新展示；手机端刷新后保持关闭。

如果公共中转站已有历史消息，桌面端弹窗仍作为本次启动的接入入口：

- 用户可随时收起弹窗查看聊天记录。
- 收起后不在消息区保留大尺寸二维码卡片。
- 二维码入口始终可从顶部“添加设备”打开。

#### 可操作规则

- 用户不连接其他设备时，也可以直接查看历史或发送内容。
- 不弹出强制模态框。
- 二维码加载失败不能阻塞聊天输入。

### 7.4 HUB-04：设备数量与设备信息

#### 计数口径

- 顶部主状态默认展示“其他设备数量”，例如：`2 台其他设备已连接`。
- 本机单独标记为“本机”，不混入“其他设备”数量。
- 设备抽屉可以展示包含本机的总数量，但必须明确写成 `共 3 台设备（本机 + 2 台）`。
- 同一设备多个标签页或多个 Socket 不应重复计数。

#### 顶部状态

- 公共中转站标题旁显示 `公共` 标识。
- 在线数量可点击，打开设备抽屉。
- 新设备连接后，数量在 1 秒内更新。
- 设备离线有 5-10 秒防抖，短暂重连不得重复生成离线提示。

#### 设备信息

设备抽屉至少展示：

- 昵称。
- 设备类型或浏览器类型；无法可靠识别时显示浏览器名称，不显示错误型号。
- 在线或离线状态。
- 本机标识。
- 最后在线时间。
- 用户 ID 后 8 位，仅用于区分同名设备。
- IP 地址放在次要位置或 Tooltip 中，不作为主要识别信息。

#### 加入与离线反馈

- 新设备加入时显示低干扰提示：`iPhone 已加入公共中转站`。
- 设备离线时显示弱提示：`iPhone 已离线`。
- 在线/离线提示不得写入 SQLite 历史，不进入 Pin、置顶、消息复制和批量下载。
- 设备离线后保留卡片并标记为离线，不重置整个连接面板。

### 7.5 HUB-05：从“等待设备”到“开始传输”

#### 状态一：等待其他设备

- 接入引导展开。
- 顶部显示 `本机已连接` 或 `等待其他设备`。
- 二维码和复制邀请链接可用。

#### 状态二：设备正在加入

- 在线设备数量实时更新。
- 接入引导保持展开，方便继续扫描第二台、第三台设备。
- 聊天输入框可正常使用。

#### 状态三：已有其他设备

- 顶部显示 `N 台其他设备在线`。
- 设备连接弹窗保持打开，二维码继续可用于连接第二台、第三台设备。
- 桌面端点击在线设备状态打开设备连接侧边栏，手机端在弹窗内展开设备列表，再次点击可关闭。
- 只有用户主动收起后才关闭弹窗；发送消息不触发关闭。
- 收起后通过顶部 `添加设备` 恢复。
- 不提供 `进入公共中转站` 或 `开始传输` 的强制按钮。

### 7.5.1 普通房间邀请弹窗

- 与公共中转站使用相同的垂直布局、标题、二维码尺寸和间距。
- 左上角标题为 `邀请加入房间`，不展示 `公共` 标签。
- 顶部中央展示房间名称，二维码居中展示，格式化房间码位于二维码下方。
- 在线设备状态、复制房间码、复制邀请链接和重新生成操作位于房间码下方。
- 复用公共中转站的扫码、设备自动加入和开始传输三步引导。
- 普通房间邀请弹窗不自动弹出，仅在用户主动打开时展示。
- `重新生成房间码` 仅对当前房主显示，服务端继续校验房主权限。

### 7.6 CLEAN-01：房主自定义自动清理周期

#### 入口

1. 仅普通房间的当前房主可见。
2. 入口位于会话侧栏当前房间的更多下拉菜单中，名称：`自动清理`。
3. 公共中转站不显示该入口。
4. 当前不是房主但仍是房间成员的用户不显示入口，只能看到当前有效清理状态。
5. 房主身份发生自动移交后，新获得的房主可见入口，原房主立即失去入口。

#### 设置弹窗

房主点击 `自动清理` 后打开确认弹窗，提供以下选项：

| 选项 | 存储值 | 含义 |
|---|---:|---|
| 7 天（默认） | `7` | 闲置 7 天后允许自动删除 |
| 30 天 | `30` | 闲置 30 天后允许自动删除 |
| 永久保留 | `0` | 不因闲置自动删除房间 |

规则：

- 新创建房间默认保存为 `7 天`，与当前版本的标准行为一致。
- 只有房主主动选择 `30 天` 或 `永久保留` 后，才使用房间级覆盖值。
- 房主可以通过重新选择 `7 天（默认）` 恢复标准清理周期。
- 当前选择必须高亮，并在弹窗内展示预计清理时间或“不会自动清理”。
- 保存按钮使用 `保存`，取消按钮不得修改设置。
- 修改设置不切换到目标房间，不改变会话排序。

#### 生效时间与提示

- 修改成功后立即更新 `expiresAt` 和设置弹窗状态。
- 其他在线设备通过 `room_updated` 同步刷新。
- 如果缩短周期后房间已经超过新周期，保存前必须提示：`房间已闲置超过所选周期，将在下一次自动清理时删除。`
- 选择 `永久保留` 时提示：`房间不会因闲置自动删除，但仍可手动解散；最后一名成员退出时仍会自动解散。`

#### 权限与安全

- 服务端必须校验操作者是当前房主，不能只依赖前端隐藏按钮。
- 服务端必须拒绝公共中转站的自动清理修改请求。
- 服务端必须校验选项只能是 `0`、`7`、`30`；房主设置接口不接受 `null`。
- 修改失败时保持原设置，并显示可理解错误信息。

#### 状态展示

- 房主和成员都能在会话列表中看到当前有效清理状态。
- 示例：
  - `约 5 天后自动清理`
  - `30 天后自动清理`
  - `永久保留`
- 如果房间当前在线，清理不会执行；在线时显示的是“预计闲置清理时间”，不是强制删除倒计时。
- 倒计时文案允许按整天向上取整。

### 7.7 CLEAN-02：自动清理的服务端规则

#### 有效周期计算

```text
newRoom.idleRetentionDays = 7

effectiveRetentionDays = room.idleRetentionDays !== null
  ? room.idleRetentionDays
  : legacyServerDefaultRetentionDays
```

```text
expiresAt = effectiveRetentionDays > 0
  ? room.lastActiveAt + effectiveRetentionDays * 24h
  : null
```

规则：

- 新房间固定写入 `7`，不跟随全局默认值变为“永不清理”。
- `null` 仅用于兼容迁移前未配置房间级策略的旧房间，继续由旧版全局默认值兜底。
- `0` 表示永久保留，不因闲置自动清理。
- `30` 表示房间级 30 天覆盖值。
- 房间级设置优先于服务端默认值。

#### 房间活动时间

以下行为更新 `last_active_at`：

- 创建房间。
- 加入或切换进入房间。
- 发送消息或上传附件。
- 修改房间名称。
- 重新生成房间码。
- 修改自动清理设置。

以下行为不得更新 `last_active_at`：

- 拉取房间列表。
- 打开会话抽屉。
- 查询历史消息。
- 在线状态心跳。
- 单纯刷新页面。
- 房主之外其他设备的后台状态同步。

#### 清理执行

- 服务启动时执行一次清理检查。
- 运行期间每 6 小时执行一次清理检查。
- 仅删除满足以下条件的普通房间：
  - 状态为 `active`。
  - 当前无在线设备。
  - `effectiveRetentionDays > 0`。
  - 当前时间超过 `expiresAt`。
- 公共中转站永远不参与普通房间闲置删除。
- 删除原因继续使用 `inactive`。
- 删除时清理房间、消息、房间码和未引用附件，并通知在线设备。
- `永久保留` 不代表房间永久存在；最后一名成员退出、房主手动解散、实例管理员清理等规则仍然有效。

#### 全局配置与兼容要求

当前服务端以全局保留天数是否为 0 来决定是否启动清理定时器。引入房间级设置后：

- 标准安装下，新房间始终初始化为 7 天，不受 `CHATTRANSFER_ROOM_IDLE_RETENTION_DAYS=0` 影响。
- `CHATTRANSFER_ROOM_IDLE_RETENTION_DAYS` 只作为迁移前旧房间的兼容兜底，不覆盖新房间和房主已显式保存的房间级策略。
- 清理器不能因为全局默认值为 0 而完全停止，否则新房间的 7 天默认值和房主选择 30 天都不会生效。
- 清理检查应始终运行，但只处理配置了有限周期的房间。
- 如果没有有限周期房间，检查应快速结束，不产生明显资源开销。

### 7.8 SORT-01：会话排序只在消息变化时更新

#### 排序字段

会话列表排序使用：

1. `lastMessageAt` 降序。
2. `lastMessageSeq` 降序。
3. 无消息房间按 `createdAt` 降序。
4. 仍相同时按房间 ID 稳定排序。

不得使用以下字段排序：

- `lastSeenAt`
- `joinedAt`
- 当前用户点击时间
- 房间名称修改时间
- 自动清理设置修改时间
- 在线人数或在线状态时间

#### 置顶规则

- 收到新消息后，对应房间立即移动到列表最前。
- 本地成功发送新消息后，对应房间移动到列表最前。
- 发送失败或未获得服务端确认的乐观消息不改变排序。
- 消息时间以服务端持久化消息的 `created_at` 和 `seq` 为准，不能使用客户端时钟作为唯一依据。
- 同一秒内的多条消息使用 `seq` 保持先后顺序稳定。

#### 不触发排序的行为

- 点击会话。
- 在会话之间切换。
- 打开或关闭会话抽屉。
- 刷新房间列表。
- 加载历史记录。
- 设备上线、离线或在线人数变化。
- 修改房间名称或自动清理设置。
- 点击二维码、复制邀请链接或打开设备列表。

#### 实时边界

- 当前已激活房间收到 Socket 消息时，列表必须立即更新并置顶。
- 当前 Socket 未订阅的非激活房间，由于第一版没有跨房间通知通道，其新消息在下一次 `room_list` 拉取时按服务端 `lastMessageSeq` 排序。
- 如果后续要求所有非激活房间也实时置顶，需要单独增加用户级通知订阅，不在本版本范围内。

## 8. 数据模型与接口建议

### 8.1 rooms 表

在现有 `rooms` 表增加：

| 字段 | 类型 | 默认值 | 说明 |
|---|---|---|---|
| `idle_retention_days` | `INTEGER NULL` | `NULL` | 新房间写 `7`；`30` 为 30 天；`0` 为永久；`NULL` 仅兼容旧房间 |
| `last_message_at` | `INTEGER NULL` | `NULL` | 最近一条持久化消息时间 |
| `last_message_seq` | `INTEGER NULL` | `NULL` | 最近消息序号，用于稳定排序 |

迁移要求：

- 旧房间保留 `idle_retention_days = NULL`，继续使用当前服务端默认值，避免升级时改变仍在使用中的房间生命周期。
- 新房间创建时写入 `idle_retention_days = 7`。
- 旧房间按现有消息历史回填 `last_message_at` 和 `last_message_seq`。
- 新房间创建时写入 `last_message_at = NULL`、`last_message_seq = NULL`。
- 不修改公共中转站的技术 ID。

### 8.2 房间响应字段

`room_list` 和 `room_updated` 至少返回：

```json
{
  "id": "room-id",
  "name": "Room name",
  "ownerId": "user-id",
  "role": "owner",
  "idleRetentionDays": 7,
  "effectiveRetentionDays": 7,
  "expiresAt": 1767225600000,
  "lastMessageAt": 1767139200000,
  "lastMessageSeq": 123,
  "lastMessage": {}
}
```

### 8.3 Socket 事件

新增：

| 事件 | 方向 | 说明 |
|---|---|---|
| `room_update_retention` | Client → Server | 修改房间自动清理策略 |
| `room_retention_updated` | Server → Room | 可选；也可复用 `room_updated` 广播 |

`room_update_retention` 请求示例：

```json
{
  "roomId": "room-id",
  "retentionDays": 30
}
```

请求校验：

- 调用者必须是当前房主。
- `roomId` 必须是 active 的普通房间。
- `retentionDays` 只能是 `0`、`7`、`30`。
- 修改操作不要求切换当前房间。
- 成功后在 SQLite 事务内更新设置和 `last_active_at`。

### 8.4 排序查询

服务端列表查询按消息字段排序，示例：

```sql
ORDER BY
  COALESCE(last_message_at, 0) DESC,
  COALESCE(last_message_seq, 0) DESC,
  created_at DESC,
  id ASC
```

禁止继续使用：

```sql
ORDER BY p.last_seen_at DESC, p.joined_at DESC
```

### 8.5 清理查询

清理器不能只按一个全局 cutoff 查询。需要按每个房间的有效周期计算，例如：

```text
effectiveRetentionDays =
  idle_retention_days IS NOT NULL
    ? idle_retention_days
    : serverDefaultRetentionDays

eligible =
  effectiveRetentionDays > 0
  AND last_active_at < now - effectiveRetentionDays * 24h
```

## 10. 异常与边界场景

| 场景 | 期望行为 |
|---|---|
| 二维码获取失败 | 展示重试，不阻塞历史聊天和输入 |
| 设备扫码后网络断开 | 设备列表显示离线或移除，顶部数量更新；不出现重复设备 |
| 同一设备刷新页面 | 视为同一设备重连，不重复计数，不产生重复上下线提示 |
| 房主修改清理周期时房间已被解散 | 返回明确错误，关闭弹窗并刷新房间列表 |
| 房主身份发生移交 | 原房主失去入口，新房主获得入口 |
| 房主选择 7 天后立即离线 | 从最后一次有效活动时间开始计算，下一次清理检查符合条件时删除 |
| 房间仍有人在线但已超过期限 | 不删除；所有设备离线后再参与清理 |
| 全局默认为 0 | 继承默认的房间不自动清理；显式选择 7/30 的房间仍需生效 |
| 选择永久保留后最后成员退出 | 仍按现有规则自动解散并清理房间 |
| 点击会话但无新消息 | 不改变会话顺序，仅改变选中和当前房间 |
| 房间名称或清理策略改变 | 不改变会话顺序 |
| 收到新消息但发送确认失败 | 不置顶 |
| 非激活房间有新消息 | 下一次打开或刷新列表时按服务端消息排序 |

## 12. 验收标准

### 12.1 公共中转站与启动体验

1. 软件启动后直接进入“公共中转站”，不存在必须点击的 `STEP2`。
2. 公共中转站技术 ID 仍为 `group_chat`，旧链接和旧历史可用。
3. 桌面端启动时在屏幕中央展示二维码接入弹窗，手机端不自动展示。
4. 二维码接入弹窗可通过收起关闭，并可从右上角 `添加设备` 重新打开。
5. 扫码设备加入后，电脑端即时显示“其他设备已连接”数量。
6. 顶部设备数量不包含本机，设备抽屉可查看本机和其他设备详情。
7. 新设备加入和离线有弱提示，提示不持久化。
8. 重复刷新、重连或多标签页不会重复增加设备数量。

10. 第一台设备加入后弹窗和二维码不消失，用户可以继续连接更多设备。

14. 用户无需等待某台预设设备，所有已连接设备可以立即传输。

### 12.2 自动清理

15. 普通房间的当前房主可以在更多菜单中看到“自动清理”。
16. 公共中转站和其他成员看不到该入口。
17. 新房间默认使用 7 天自动清理；房主可以保存“7 天”“30 天”“永久保留”三种策略。
18. 保存后房间列表和其他在线设备同步显示新的有效状态。
19. 修改自动清理策略不会切换当前房间，也不会改变会话排序。
20. 服务端拒绝非房主、公共中转站和非法选项。
21. 全局兼容默认值为 0 时，新房间仍默认 7 天清理，房主显式选择 30 天时也按 30 天执行。
22. 房间有在线设备时不会被自动删除。
23. 选择永久保留后，手动解散和最后成员退出规则仍生效。
24. 清理房间时同时清理消息、房间码和不再被引用的附件。

### 12.3 会话排序

25. 收到新消息的会话移动到列表最前。
26. 本地成功发送新消息的会话移动到列表最前。
27. 点击、切换、刷新、打开抽屉不会改变排序。
28. 在线人数、名称修改和清理策略变化不会改变排序。
29. 同一时间范围的多条消息按 `seq` 稳定排序。
30. 当前房间的新消息立即反映；非激活房间在下次列表刷新时按服务端消息时间排序。

32. Pin、置顶、批量下载、附件查询和历史清理不受影响。

## 15. 风险与待确认项

| 风险 | 影响 | 缓解方式 |
|---|---|---|
| “公共中转站”被理解为永久共享存储 | 用户可能误放敏感内容 | 保留“公共”标识，并在帮助文案中说明可被同服务设备访问 |
| 自动清理缩短周期后立即触发 | 房主可能误删房间 | 保存前展示已闲置提示并二次确认 |
| 全局默认值为 0 时清理器不运行 | 新房间 7 天和房主设置的 30 天失效 | 清理器始终运行，新房间显式写入 7 天 |

| 非激活房间无法实时收到新消息 | 列表不能即时置顶 | 明确第一版边界；后续增加用户级通知订阅 |
| 设备类型识别不可靠 | 展示错误设备型号 | 只展示可确认的浏览器/平台信息，不能确认时显示“浏览器” |
| 旧房间迁移遗漏 | 清理或排序异常 | 启动迁移补齐字段并增加回归测试 |
| 阿拉伯语术语不统一 | 多语言界面不一致 | 发布前进行本地化审校 |
