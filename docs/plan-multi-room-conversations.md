# 多房间会话需求方案

## 1. 结论

建议将 ChatTransfer 的“群聊”概念统一升级为“房间”。房间是消息、文件、成员和在线状态的基本隔离单位。后续不再单独设计私聊模型；一对一传输可以理解为一个只有两台设备的房间。

用户可以通过扫码或房间码加入房间，也可以创建新房间用于不同项目、不同设备组合或不同协作场景。这样可以避免所有内容都进入当前默认群聊，同时保留新设备扫码加入的低成本路径。

## 2. 现状

当前产品只有一个全局默认群聊：

- 客户端通过 `group_online` 进入同一个 Socket.IO 房间 `group-chat`。
- 消息、文件、历史记录、附件和批量下载都围绕当前默认会话组织。
- 服务端使用 `RoomManager` 维护用户在线状态，最近版本已支持同一用户多个 Socket 连接和离线防抖。
- SQLite 已有 `sessions`、`session_participants`、`messages` 等表，可以按会话保存消息。
- 前端顶部已经预留左侧位置，可用于后续会话切换入口。
- 用户可以通过扫码进入当前默认群聊，但没有多房间、房间码或手动加入房间能力。

## 3. 痛点

1. **所有内容集中在默认群聊**  
   不同项目、不同设备组合、不同协作对象的内容混在一起，后续查找历史消息和文件较困难。

2. **无法创建独立传输空间**  
   用户有时只想和一台设备传输日志、截图、安装包或临时账号，但不希望这些内容进入公共群聊。

3. **缺少多会话切换能力**  
   当前页面只能展示一个默认群聊，用户无法快速在多个传输场景之间切换。

4. **设备加入方式单一**  
   目前主要依赖扫码。某些设备不方便扫码时，缺少通过房间码手动加入的入口。

5. **“群聊”概念不够准确**  
   ChatTransfer 的核心场景不是传统即时通讯，而是跨设备临时传输。“群聊”会让用户误以为必须有多个人参与；而“房间”更贴近扫码进入、临时协作、用完即走的产品心智。

## 4. 目标

1. 将“群聊”概念统一为“房间”。
2. 支持创建多个房间，每个房间拥有独立消息、文件和成员状态。
3. 支持扫码加入房间。
4. 支持通过房间码手动加入房间。
5. 支持房间内在线设备列表和上下线提示。
6. 支持无刷新切换房间。
7. 保持现有默认群聊链接和扫码流程兼容。
8. 为后续房间历史清理、房间过期和删除会话提供清晰边界。

## 5. 收益

| 收益 | 说明 |
|---|---|
| 概念统一 | 不再区分群聊与私聊，所有会话都可以表示为房间 |
| 降低加入成本 | 新设备可以扫码或输入房间码快速加入 |
| 内容隔离 | 不同项目、不同设备组合的消息和文件互不干扰 |
| 提升隐私感 | 临时内容可以放在独立房间，避免进入公共默认房间 |
| 更好支持多人协作 | 多台测试设备、多个测试项目可以使用不同房间 |
| 复用现有能力 | 历史记录、附件、批量下载、在线设备列表都可以按房间扩展 |

## 6. 用户流程

### 6.1 创建房间

1. 用户点击“新建房间”。
2. 输入房间名称，例如“iOS 测试机传输”“项目 A 临时调试”。
3. 系统生成 `roomId` 和房间码。
4. 用户进入新房间。
5. 系统展示邀请二维码和房间码。
6. 用户可以复制房间码、复制邀请链接，或展示二维码给其他设备扫码。

### 6.2 扫码加入房间

1. 新设备扫描房间邀请二维码。
2. 浏览器打开加入链接。
3. 如果设备没有昵称，提示填写昵称或使用默认昵称。
4. 客户端校验 `roomId` 和房间码。
5. 加入成功后进入房间。
6. 房间保存到本机最近会话列表。

### 6.3 手动加入房间

1. 用户点击“加入房间”。
2. 输入房间码。
3. 服务端根据房间码查找房间。
4. 校验通过后加入房间。
5. 前端加载房间元信息和历史消息。

### 6.4 切换房间

1. 点击顶部左侧会话切换入口。
2. 打开会话侧栏或抽屉。
3. 展示最近房间、当前房间、在线人数和最后消息时间。
4. 选择目标房间。
5. 前端无刷新切换 Socket 房间和历史消息。
6. 清理当前页面的附件选择、Pin 状态、临时提示和输入状态。

### 6.5 退出或删除房间

第一版建议区分两个动作：

#### 从我的设备移除

- 仅从当前浏览器的最近会话列表中隐藏该房间。
- 清理本地消息缓存、Pin 状态和附件选择。
- 不删除服务器上的消息和文件。

#### 清空房间服务器记录

- 删除该房间下的所有消息和关联文件。
- 房间内在线设备收到实时通知。
- 需要使用危险操作二次确认。
- 明确提示“所有设备都无法恢复”。

第一版优先保证“创建房间、加入房间、切换房间”体验稳定；“删除房间”可以先支持本地移除和服务器清空，不建议第一版实现复杂的多用户删除游标。

## 7. 房间模型

### 7.1 房间字段

建议服务端维护以下核心字段：

| 字段 | 说明 |
|---|---|
| `roomId` | 房间唯一标识，建议使用 UUID |
| `name` | 房间名称 |
| `code` | 房间码，用于手动加入 |
| `createdAt` | 创建时间 |
| `updatedAt` | 最后更新时间 |
| `lastMessageAt` | 最近消息时间 |
| `createdBy` | 创建者用户 ID，仅用于展示和后续管理 |
| `status` | `active`、`archived`、`deleted` |

### 7.2 房间码规则

- 使用 8 位随机大写字母和数字。
- 移除容易混淆的字符，例如 `0/O`、`1/I/L`。
- 展示格式建议使用 `XXXX-XXXX`，提高可读性。
- 房间码必须与 `roomId` 一起校验，避免仅靠短码被穷举。
- 支持重新生成房间码；旧房间码立即失效。

### 7.3 默认房间兼容

为避免旧扫码链接失效，现有默认群聊应映射为：

```text
默认房间 roomId = group_chat
```

旧参数 `receiver=group_chat`、旧 Socket 房间名和旧历史记录继续兼容。默认房间可以不要求房间码；新建房间必须使用房间码。

如果后续希望默认房间也受房间码保护，可以单独设计迁移提示，但不应在第一版强制变更所有旧链接。

## 8. 技术方案

### 8.1 服务端数据模型

建议新增以下表或集合：

#### `rooms`

```sql
CREATE TABLE IF NOT EXISTS rooms (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  code TEXT NOT NULL UNIQUE,
  created_by TEXT,
  status TEXT NOT NULL DEFAULT 'active',
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
);
```

#### `room_participants`

用于记录曾经加入过房间的设备或用户：

```sql
CREATE TABLE IF NOT EXISTS room_participants (
  room_id TEXT NOT NULL,
  user_id TEXT NOT NULL,
  nickname TEXT,
  joined_at INTEGER NOT NULL,
  last_seen_at INTEGER,
  PRIMARY KEY (room_id, user_id)
);
```

现有 `sessions` 和 `session_participants` 可以继续用于消息历史隔离；`rooms` 和 `room_participants` 用于房间元数据和房间列表。

### 8.2 Socket 事件

建议新增或调整以下事件：

| 事件 | 说明 |
|---|---|
| `room_create` | 创建房间，返回 `roomId`、房间码和房间名称 |
| `room_join` | 通过 `roomId` 和房间码加入房间 |
| `room_leave` | 当前设备离开房间 |
| `room_switch` | 客户端切换当前活跃房间 |
| `room_updated` | 房间名称、房间码或状态变化 |
| `room_presence_changed` | 房间内设备上线或离线 |
| `room_history_cleared` | 当前房间服务器历史被清空 |

现有 `group_online`、`group_chat`、`user_list_updated` 等事件可以保留，用于兼容旧客户端；新前端逐步迁移到房间维度事件。

### 8.3 Socket 房间隔离

Socket.IO 中需要从单一 `chatRoom = 'group-chat'` 迁移为按 `roomId` 管理：

```text
room:<roomId>
```

例如：

```text
room:group_chat
room:9f1c2c86-1f80-4d14-9c35-4f7d17d63b18
```

一个 Socket 同时只应位于当前活跃房间。切换房间时：

1. 离开旧 Socket 房间。
2. 加入新 Socket 房间。
3. 重新广播旧房间和新房间的用户列表。
4. 前端加载新房间历史。

### 8.4 房间码校验

手动加入必须校验：

- `roomId` 是否存在。
- 房间状态是否为 `active`。
- 房间码是否匹配。
- 加入频率是否超过限制。

建议在服务端加入简单内存限流或 SQLite 限流记录，避免短时间内被暴力尝试。

### 8.5 历史与文件隔离

所有消息查询、附件查询、批量下载、历史清理都必须带上房间维度：

```text
requester
roomId
```

替代或兼容当前的：

```text
requester
chatType
targetUser
```

为了避免一次性破坏现有客户端，服务端可以暂时兼容旧参数：

- `chatType=group` 且 `targetUser=group_chat` 映射到默认房间。
- 新前端统一使用 `roomId`。

### 8.6 在线状态

当前在线设备能力按全局用户维护。多房间方案下需要按房间维护：

```text
roomId -> userId -> socketIds
```

同一个人可以同时在线于多个房间，但每个房间只展示当前进入该房间的人。

上下线提示也应限定在当前房间内广播，避免把其他房间的设备状态通知到无关房间。

## 9. 前端方案

### 9.1 顶部布局

保留当前三栏布局：

| 位置 | 内容 |
|---|---|
| 左侧 | 会话切换入口，后续可扩展房间列表 |
| 中间 | 房间名称、连接状态、在线人数 |
| 右侧 | Pin、二维码、常用功能等操作 |

### 9.2 会话侧栏

第一版可以先使用抽屉，避免移动端布局复杂化：

- 默认房间固定展示。
- 最近房间按 `lastMessageAt` 排序。
- 每个房间显示房间名称、在线人数、最后消息时间。
- 当前房间高亮。
- 提供“新建房间”和“通过房间码加入”。

### 9.3 房间邀请

邀请弹窗展示：

- 房间名称。
- 邀请二维码。
- 房间码。
- 复制房间码。
- 复制邀请链接。
- 重新生成房间码。

### 9.4 状态清理

切换房间时必须清理：

- 当前输入内容。
- 未上传完成的文件卡片。
- 附件多选状态。
- Pin 和置顶状态。
- 滚动位置。
- 上下线临时提示。
- 批量下载弹窗状态。

## 10. 权限与安全

当前产品没有账号体系，房间码是主要访问边界。

第一版应遵循以下原则：

- 知道 `roomId` 和房间码的人可以加入房间。
- 不知道房间码的人不能通过手动加入进入。
- 房间码可以随时重新生成。
- 房间内历史和附件只能由房间内用户访问。
- 不实现端到端加密；服务端仍然可以看到消息内容。
- 局域网内仍建议配合防火墙、内网隔离和临时房间使用。

## 14. 验收标准

1. 用户可以创建新房间并获得房间码和邀请二维码。
2. 新设备可以通过扫码加入房间。
3. 新设备可以通过输入房间码加入房间。
4. 不同房间之间的消息、文件和在线设备互不可见。
5. 切换房间时不刷新页面，历史消息正确加载。
6. 旧默认群聊链接和旧历史记录仍然可用。
7. 房间内批量下载只能选择当前房间的附件。
8. 清空房间历史只影响当前房间。
9. 重新生成房间码后，旧房间码不能加入。
10. 移动端和桌面端布局均可用，且无状态残留。

## 15. 风险与约束

| 风险 | 说明 | 缓解方式 |
|---|---|---|
| 房间码泄露 | 知道房间码的人可以加入 | 支持重新生成房间码，后续可增加过期时间 |
| 无账号体系 | 清理浏览器数据后可能丢失本机会话列表 | 用户可重新扫码或输入房间码加入 |
| 旧链接兼容 | 旧二维码和链接不能失效 | 保留 `group_chat` 默认房间映射 |
| Socket 状态迁移复杂 | 全局事件和用户列表需要按房间拆分 | 分阶段迁移，先兼容旧事件 |
| 本地状态残留 | 切换房间后可能出现消息、Pin 或附件错乱 | 建立统一切换清理流程 |
| 服务端数据增长 | 多房间会增加历史和文件占用 | 后续增加房间过期和自动清理 |

## 16. 暂不实现

- 端到端加密
- 房间权限分级
- 房主权限管理
- 房间成员踢出
- 房间邀请链接过期时间
- 跨服务器房间同步
- 每个用户独立的删除游标
